# Weora CLI 与团队上下文接入方案

## 目标与边界

Weora 保存团队共同上下文，使使用 Codex、Claude Code 等不同 Agent 的开发者能够按项目、按需获取同一份有效信息。开发者继续使用自己的 Agent，不必迁移到 Weora 内置界面。

共同上下文可以包含需求、当前有效决策、项目记忆、约束及其来源。具体资料是否已经上线，以对应领域实际接口为准，不以 CLI 规划作为能力交付证明。

```text
开发者 → Codex / Claude Code → Skill 指引 → weora CLI
                                           ↓
                                    Weora 公开 API
                                           ↓
                             对应应用服务 → 团队上下文存储
```

这里的 Skill 是 Agent 可加载的使用说明，CLI 才是执行入口。后续 Weora 内置 Agent 的 Tool 可以调用同一应用能力。

## 职责

| 部分 | 负责内容 |
| --- | --- |
| Weora 平台 | 上下文存储、版本与状态、检索、身份与权限、审计 |
| CLI | 命令发现、参数解析、未来的 API 调用、输出与退出码 |
| 配套 Skill | 何时读取上下文、如何组织查询、如何引用来源、何时提交候选记忆 |
| 外部 Agent | 结合当前任务判断要查什么，读取结果，完成开发工作 |

Skill 不内置凭据，不把团队资料复制为长期静态提示词。实际身份和授权由服务端校验；不能相信模型提交的用户身份。

## 本轮交付

```text
apps/cli/
├── pyproject.toml        # 独立安装包与 weora 入口
├── uv.lock               # 可复现开发环境
├── README.md             # 运行、输出协议与验证方法
├── src/weora_cli/
│   ├── __main__.py       # python -m weora_cli 入口
│   ├── cli.py            # 参数解析、分发、JSON 输出与错误
│   └── commands.py       # 命令声明与输入 Schema
└── tests/test_cli.py     # 进程输出、退出码与发现契约
```

| 已实现命令 | 含义 |
| --- | --- |
| `weora --help` | 人可读帮助 |
| `weora version` | 客户端版本、输出协议版本 |
| `weora commands` | 已实现命令及空的业务能力列表 |
| `weora schema` | 全部命令声明和 JSON Schema 输入定义 |
| `weora schema version` | 指定命令的声明 |

命令注册与帮助共用声明。当前所有命令都在本地执行，不读取用户配置、不联网。

成功 JSON 发往 stdout，失败 JSON 发往 stderr；退出码分别为 0、参数错误 2、内部错误 1。未知业务命令直接失败，不模拟写入、不返回占位成功。后续远端错误码在首个 API 接入时扩展。

当前不包含：认证登录、HTTP 客户端、运行凭证注入、记忆和权限命令、上下文搜索、业务 Skill、Agent 自动安装或修改已有 Agent 配置。

## 后续首个切片：外部 Agent 读取团队上下文

以下为候选命令形态，当前不可执行，最终参数随真实 API 定义：

```text
weora context search --project <id> --query "渠道配置有哪些已确定约束"
weora context get <context-id>
```

先选一个真实项目上下文来源接通，不先实现一个覆盖全部知识、代码和历史对话的统一搜索引擎。

返回结果应携带能供 Agent 判断与引用的信息：内容、所属项目、来源引用、版本或更新时间，以及适用的有效状态；采用何种字段以服务端领域契约为准。无结果、无权限和调用失败要能明确区分。

具体调用流程：

1. 开发者为当前工作建立明确的项目和身份上下文。
2. 加载 `weora-context` Skill，说明开始任务或遇到业务约束时如何查询。
3. Agent 用 CLI 搜索，必要时按 ID 读取完整条目。
4. Agent 根据当前有效资料开展开发，在回答或交付中保留来源。
5. 发现新决策时，可提出记录建议；等写入能力上线后，再通过明确的写入命令执行。

Skill 是使用引导，不保证每个 Agent 必定执行查询。如果后续需要“任务启动前必须加载指定上下文”，应由受控 Runtime 或任务入口强制装配，而不是仅靠 Skill 的文字要求。

外部开发者与飞书触发的受控 Agent 使用相同业务能力，但不假定它们共用认证方式。认证方案随首个接入能力落实，CLI 不允许通过 `--actor` 冒充管理员。

## 业务能力如何加入

只有对应服务端接口具备明确输入、输出、授权与错误语义后才注册命令。新增命令同时补帮助、Schema、API 响应与错误契约测试，再提供真实可用的配套 Skill。

后续可按业务加入：

- `memory`：项目记忆的查询、创建和更新。
- `agent access`：机器人的调用授权管理。
- 其他领域：由实际用户任务决定，不预建空命令组。

不为未来能力预建空领域、通用插件加载器或无调用方的 SDK。CLI 调平台 API，不把后端 Application、ORM 或 Runtime 搬入客户端。

## 阶段验收

| 阶段 | 完成条件 |
| --- | --- |
| 当前骨架 | 可安装、可运行、帮助与 Schema 一致、输出/退出码通过进程测试；没有虚构业务能力 |
| 上下文读取 | 真实 API、项目身份、有效内容与来源；空结果、权限错误和远端异常有测试 |
| Agent 接入 | Codex 和 Claude Code 分别实际完成一次上下文读取，结果可核对；此类真实 Agent 验证另行明确执行 |
| 写入能力 | 记忆或授权真实落库，失败如实反馈，规则由服务端执行 |
