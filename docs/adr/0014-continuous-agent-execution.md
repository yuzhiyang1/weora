# ADR 0014 持续任务协调与执行层升级

- 状态：Proposed。
- 日期：2026-11-02。
- 2026-11-03 增量：[ADR 0015](0015-task-continuations.md) 已确认并实施持久任务续接；本 ADR 的整体 Router/Job/Observer 提案仍为 Proposed。
- 关联：[执行层架构升级方案](../architecture/execution-layer-upgrade.md)、[ADR 0003](0003-agent-execution-and-feishu-context.md)、[ADR 0002 Runtime 边界](0002-agent-version-and-runtime-adapter-boundary.md)、[ADR 0012 执行预算](0012-model-and-execution-budgets.md)。

## 背景

Weora 已有 Task/Run、持久调度、Pi 工具循环、审批、沙箱、上下文和交付账本，但当前新请求通常新建 Task，缺少跨消息任务归属、协调会话、持久模型历史及后台作业控制。持续协作需要补充这些能力，同时保留现有技术栈及平台分层。

用户明确将本次工作定位为执行层架构升级，并允许开发阶段调整目标。旧版“不持续订阅话题”“普通消息不启动任务”等首期限制可由新方案替代；变化不自动授予来源读取、任务发起或写入权限。

## 提案

1. 保持 Python/FastAPI、PostgreSQL、Redis/Celery、模块化单体及控制面/执行面分工。保留 Pi，其他 Runtime 通过 Weora 端口接入，不采用上游运行平台替换现有底座。
2. Router 是受工作空间、受众和项目范围约束的协调角色。它分派和续接任务，深入调查与改码继续由 Worker 承担；不提供企业级全局共享上下文。
3. Task 表示持续目标，TaskInput 追加后续消息，Run 表示执行尝试，SessionJournal 保存模型执行上下文。保留每 Task 一个非终态 Run；独立任务并行，后续复杂任务通过子 Task 表达独立工作。
4. Router 的 CoordinationSession/Turn 属于执行控制记录，不伪造用户 Task。协调轮次及 Worker 激活分别使用持久输入、版本 CAS、租约与代次，拒绝迟到状态覆盖。
5. 事件先持久化、过滤和授权，再按明确引用/订阅直通，无法归属的交给 Router。上下文扇出不等于授权扇出；同一请求需有明确处理归属，跨受众内容不得自动共享。
6. TaskBasis 记录启动依据，不替代 Identity、来源授权及 PlanScope。目标或动作变更后重新提案，旧批准不得因新 Run 或新角色自动继承。
7. 新增 SessionJournal 和受保护检查点，不把现有 RunEvent 的状态事件误当成可重建的完整历史。摘要、RAG 和长期记忆检索结果继承来源限制、引用和保留期；不混入 Agent/Skill 不可变版本。
8. 长工具逐步变成持久 Job，完成事件唤醒会话。Job 独立持有资源租约与批准版本；等待释放计算资源，未知写入保留 UNKNOWN 并对账。当前同步执行与清理逻辑在资源所有权迁移完成前继续保留。
9. 主动执行通过 off/observe/auto 与版本化规则逐步开放。先用声明式 Observer 和现有 Beat/Celery 监听，不开放模型生成的任意常驻程序。
10. Runtime 按能力和冻结 profile 选择，先完成 Pi 的步骤持久化，再验证 Codex/Claude 与本地 Worker。原生工具只有满足平台授权、隔离和审计边界时才开放相应能力。
11. 复用已有调度 Outbox、渠道回复和远端交付账本，各自保留单一 owner；跨模块通过应用命令、幂等投递与补偿协作。执行成功、消息送达和人类验收分别记账。
12. 以 U1 任务续接、U2 双层协调、U3 异步作业、U4 主动监听、U5 多 Runtime 分阶段交付。旧 Task 保留 legacy 语义，新模式按范围启用；不对同一事件同时使用两套执行路径。

## 影响与取舍

- 平台与技术栈保持，执行层新增状态和协议，需要数据库迁移及跨进程故障验证。
- 持续协调不是无限常驻模型调用。消息、等待、监听和通知都有预算和停止条件。
- 当前 RAG/长期记忆的产品边界保留；本提案不声称其独立模块已实现，也不将其全部建设纳入升级前置条件。
- 采用 Super-agent 的协调、订阅与上下文思想，以及 Comma 的任务、Runtime、Loop 与恢复契约；不复制其数据库设计或整套内核。
- 旧设计文件将在实施对应阶段更新，历史验收保持原事实。此 ADR 为待评审方案，不把 Accepted ADR、代码或运行环境自动标为已变更。

## 验证要求

首先验证同 Task 多消息、并发续接幂等、撤权、目标变化和叫停；随后验证消息消费、工具意图提交、后台 Job、重启和外部结果未知窗口。真实 PostgreSQL、Redis/Celery、Pi 和渠道闭环分别验收；模拟模型、人工补收或状态回读不能代替真实自动执行证明。

监督保留用户主动停止标记，不恢复被用户取消的目标，不自动重放未知写入。上线前验证新旧模式隔离、正文与摘要清理、协议兼容及可执行的回退流程。
