# Weora 多入口、多引擎的完整原生编码会话

状态：已选定。

## 决策与接入边界

Weora 使用 Python 控制面和执行面，通过独立进程驱动 Pi 1.3.0、Oh My Pi 18.16.0 各自的官方 CLI `--mode rpc`。Pi 与 OMP 分别保留原生 Agent 的工具调度、Skill 加载、上下文压缩和会话持久化。Weora 负责工作空间授权、模型连接、工具网关、运行租约、协调与交付记录。

启用原生 RPC 镜像后，飞书和控制台进入相同的运行选择与授权边界。飞书协调 Main、工程 Worker 和子会话均使用完整原生 RPC；不能因群来源或协作身份退回仅有模型循环的实现。未配置原生镜像的部署保留已有 Runtime 兼容路径，不属于本轮原生方案的验收条件。

- **控制台**：创建任务时解析项目授权、AgentVersion、团队 Harness 和模型连接，冻结执行配置后提交 Run。
- **飞书 Main**：验证群来源和协调效果租约，使用按工作空间、话题范围与引擎区分的原生会话。Main 没有项目仓库挂载；通过受控协调工具读取授权来源、派发任务和处理回执。
- **Worker**：复用 Run 租约、来源授权和项目快照，向原生会话注册 Weora 工具与协调工具。原生工具执行和平台工具调用都在同一 Agent 会话内产生证据。
- **引擎选择**：新任务依据团队 Harness 选择 Pi 或 OMP。同一任务的继续运行保留已冻结的引擎和仓库基准，不能因全局设置变化而把另一引擎接到旧会话卷。Main 的两种引擎使用独立会话命名空间。

## 原始目标与完成判定

原发起人的完整任务原文及后续纠偏是目标依据。模型产生的路由摘要、任务标题、委派说明和 scope 字段只用于安排工作，不得增加“只找 1–3 项”“超范围单列”等原文没有的限制。同伴消息可成为证据，不能静默变成发起人的新指令。

Worker 接收完整目标以及目标输入 ID。长正文通过连续分段读取保留全文覆盖区间，读到最后一页不等于读完整篇。引擎将初始输入或插话写入原生会话后，平台才记录已读；完整正文覆盖与已读回执分别校验。

`orchestrator_report` 用 `completed_input_ids` 和 `remaining_work` 表达目标覆盖。只有当前有效目标均已完整读取、全部覆盖且没有剩余工作时才接受 `ready`。提交报告之后又收到纠偏时，对账再次验证覆盖并转为 `partial` 继续。Run 执行成功、工具成功或一段回答结束，都不能单独把 Ticket 置为完成。

部分结果和预算收尾报告使用 `partial`，在保留原目标和会话的前提下继续。连续无进展或达到续接预算时保留未完成状态并说明阻碍，不改写成已完成。平台工具预算耗尽后拒绝 `ready`；这不替换原生工具循环，也不把同一预算套到原生 `read`、`bash`。模型截断和空最终结果有明确失败码；经过工具接受的报告摘要可以作为有效最终输出。

最终结果回传使用 Worker 已验证的完整报告作为内容依据。Main 与无 Main 回退路径不得再次概括、缩短或改写这份报告；发送前复核历史待发消息，替换其中可能残留的旧摘要。同一结果键幂等，重放调度不能重复回复；普通 answer 工具也不能绕过已就绪结果的完整回传边界。

该约束由 `Engine.result_text` 统一生成正文，并在结果入 Outbox 及实际发送事务内执行，不依赖 Main 遵守提示词。最终 `answer` 归一到同一个 `result(ticket_id, assignment_id)` 幂等键；普通问答及接单回执仍可由 Main 编写。完整报告在平台的 16000 字符上限内原样保留；运行链接只有在剩余空间足够时追加，不为链接截短报告。已有 `unknown` 或 `sent` 消息不重新改写或盲发。

覆盖引用和 `verified` 标记是平台状态契约，不代表模型报告中的每个数字和业务判断已经由独立系统证明。Worker 仍须逐项给出源表与源码证据；真实入口验收必须复核关键数值及结论。结果权威边界防止 Main 再次压缩引入事实错误，不能代替对 Worker 原报告本身的准确性检查。

## Skill、工具与模型连接

AgentVersion 冻结发布 Skill 的版本、大小和 SHA-256。Main、Worker 和子会话均携带完整发布包，解包时保留 `SKILL.md`、脚本、参考资料及资源的相对路径。Pi 显式加载发布包的 `SKILL.md`；OMP 从隔离的 `.omp/agent/skills` 发现。脚本由原生工具在该会话的隔离环境内执行，不能仅将 Skill 标题或正文摘要塞进提示词代替安装。

Pi 通过会话专用 MCP 端点调用 Weora 工具；OMP 通过 `set_host_tools` 注册。平台工具仍经过 ToolGateway 的参数校验、租约、工作空间权限、预算与审计；协调工具由同一个会话的宿主回调处理。一般工程会话保留原生默认工具，Pi 增加 `find`、`grep`、`ls`，不使用平台自建工具列表替换原生工具集。

管理员分别通过 `WEORA_NATIVE_RPC_PI_EXTENSIONS` 和 `WEORA_NATIVE_RPC_OMP_EXTENSIONS` 指定镜像 `/opt/weora-coding-tools/extensions/` 下的可信扩展。解析后的路径必须仍在该目录，任务正文不能开启不受控扩展发现。模型代理按冻结的供应商、接口和模型转发；鉴权及模型密钥留在 Worker 侧，不进入原生容器或运行事件。

## 工作区、会话与权限

工程任务拥有所选仓库固定提交的隔离副本。管理员启用镜像即为已授权任务在副本内编辑及运行命令提供执行环境；它不取消来源、项目和高风险平台工具的权限规则。容器无外网、无宿主工作目录挂载、无代码托管凭据。远端提交、合并等交付仍由现有交付与审批能力约束。

主任务的工作目录和原生日志保存在稳定容器主机的任务卷，沿用既有卷名，部署升级不另建空会话代替已有历史。停止先请求引擎中止并落盘，再关闭容器；后续继续运行复用原始会话和工作区。外部副作用结果未知时先对账，不因进程重启盲目重放。

飞书话题的有限读取窗口与原生会话历史分别校验。同 Task 的新输入可使用仍获授权、同引擎的既有历史补足 `budget_exceeded` / `has_more` 窗口截断，但快照继续标为 partial，不伪造完整讨论。成功轮次，或停止/失败前已有真实原生工具、模型回复的轮次，均可证明会话已有材料；仅启动进程不算。首次请求、引用缺失、来源过期/撤权或不同引擎的历史仍不能放行。该检查只产生授权事实，不把旧 SDK 摘要再次注入 Pi/OMP，完整历史仍由原生日志恢复。

显式重试原生飞书任务时，如果旧 Run 仍停在准备输入阶段的 `WAITING_CONTEXT`，Runs 在同一事务结束该等待轮次并记录新 TaskInput。状态比较更新保护已经恢复或进入审批的轮次；`RECOVERY_REQUIRED` 和只读恢复仍走原来的对账路径。新 Run 继续原 Task 和原生历史，重复的飞书触发复用同一次重试安排。

### 人工停止后的显式恢复

停止 Ticket 与取消 Run 分属持久事务。执行器提交终态前核对同用户、当前 Assignment、Run 与领取代次，若存在已持久人工停止，须通过 Runs 应用接口补齐取消请求，不能等异步 cancel 效果晚到后把停止误报成 `ACCESS_REVOKED`。确认取消仍晚于受控进程清理；普通来源撤权、失效领取和其他安排不能借此变成取消。

人工停止保持 `Ticket.ended_by=human` 与旧 Assignment 的 `human_stopped` 终态。普通跟进、后台轮询、同伴证据和失败重试不能自动清除该状态。停止后的恢复是新的明确授权输入，由 Main 使用 `orchestrator_route` 的 `decision=resume` 提交；它与失败/阻塞任务的 `orchestrator_ticket_retry` 分开。

恢复事务必须核对：消息来自原发起人且为人类直接输入、通过当前显式准入、时间晚于停止时刻，原任务及必需目标来源仍有效；渠道发送结果未知时仍先对账。带 `#任务号` 的请求必须唯一匹配同一 Task，编号只指定目标，不自动表示恢复意图。Main 对已停止编号任务只能根据实际新意图恢复或不恢复，不能通过 `accept` 另建任务替代续接。编号请求的显式 `stop` 也允许 Main 控制，不能仅当作普通 Worker 插话。

恢复只追加新 Assignment；保留原 Ticket、Task、引擎、冻结仓库基准、Worker session ID 和原生历史代次，原 Run 的终态及审计记录不改写。重复恢复请求复用同一决定与安排。派发前必须确认旧 Run 已进入终态，否则返回 `WAITING_FOR_STOP` 延后；不能提前创建可能被识别为停止前排队内容的新 TaskInput，也不能并行启动两个可写进程。

控制台允许原发起人在获授权的飞书任务中提交补充、重试、停止或恢复。平台从原任务读取来源、身份和保留期。控制台的明确操作通过相同的协调状态机，无需由模型推断意图。补充默认排入下一轮，插话只投递给当前 Run 的领取代次。重试与人工停止后的恢复分别校验，原文结果仍回到原飞书话题。

停止输入标记为 `control_action=stop`，作为执行控制历史保留，不成为恢复后仍需实施的工作目标。恢复输入标记为 `resume`，其中原文和新的纠偏仍纳入目标覆盖；此前未读的有效工作目标重新投递。恢复不会复制旧 Run 的批准、执行身份或工具副作用回执。原生文件和上下文是否真正保留，须由真实运行中的旧改动、先前插话及 `native.resumed` 等证据验证，不能仅凭新 Run 创建成功宣布续接完成。

子会话使用任务冻结提交创建独立工作区，卷 ID 由任务及子会话 ID 派生，不与父会话共享可写目录。子改动不自动并入父工作区。子会话结果和 Diff 必须标明隔离来源及尚未应用的事实；父会话检查、应用并在自己的最终工作区复测后，才能作为主任务交付证据。

状态查询、同伴证据处理及只读恢复需要执行层只读隔离。主工作区卷只读挂载；单独的只读会话日志卷允许引擎保存本轮历史，且不覆盖主会话日志。没有既有工作区时，从冻结快照准备引擎用户不可写的临时目录。只读会话限制为读取类原生工具及已授权平台工具，不产生工作区 Diff；不能仅靠提示词禁止编辑。

原生 JSONL 历史独立于平台消息记录。来源撤权后，事务递增 `native_history_epoch` 并清除平台历史；新的会话代次使用独立卷，不再加载含已失效来源的旧原生日志。正在运行的会话在输入拉取和模型外发前验证代次，失效立即停止。旧卷的物理清理遵循部署的保留和回收策略，递增代次不等于删除旧卷。权限策略变化或历史代次变化以专门失败码结束旧执行，编排器按当前有效来源安全续接仍然有效的原目标。

## 模型付费拒绝与恢复

原生模型代理不设置未配置的请求次数上限，不以第 161 次请求等隐藏阈值截断长任务。冻结模型与路径白名单、运行整体时限、单请求超时、显式 Token 预算及响应大小限制持续生效；原生循环和重试由对应引擎负责。

原生模型代理保留供应商 HTTP 状态，但不解析、记录或透传错误响应正文。HTTP 402 映射为 `MODEL_PAYMENT_REQUIRED`，只说明供应商因付费或额度条件拒绝请求，不能推断余额必为零；401、403、429 及服务端错误分别保留脱敏的鉴权、访问、限流和供应商不可用原因。后续请求成功时清除旧错误码，避免恢复后的正常会话继续携带旧拒绝原因。

原生最后一条 assistant 为错误或中止时，运行按该终态失败；不能退回较早的旁白或报告摘要伪装为本轮成功。402 不改变用户目标、Task、原生卷或模型选择，也不触发平台无限自动重试。协调通知引导核对模型账户的付费/额度条件及配置，处理后按新明确输入继续原任务。供应商恢复之前，验收保持未完成；既有静态检查和本地协议测试不能替代恢复后的真实模型续接。

## 事件与 Diff 证据

运行事件只携带事实类型和必要元数据，不记录完整原始 RPC 帧或凭据。插话、停止、续接要以已持久化的引擎回执和运行状态为证，不能只显示请求已入队。

源码版本引用使用平台冻结的完整 `source_revision`；原生运行目录提供只读 `source-revisions.json` 清单，包含仓库 ID、源提交和对应工作目录。隔离副本中的 Git HEAD 是沙箱基线或后续本地提交，不能冒充源仓库提交，也不能据本地分支名推断源分支。

Diff 根据冻结仓库快照与实际工作目录计算，保留仓库 ID、基准提交和截断状态。停止后可以保存已经发生的本地改动；失去来源授权或运行租约时不再公开产物。子会话 Diff 显式标注独立工作区，不能当成主目录已应用的最终 Diff。只读模式不输出 Diff，主会话恢复后仍以主工作目录产生最终证据。

## 部署与兼容

飞书和控制台使用所选原生引擎。代码托管任务继续使用受控 Pi 交付执行器，审批、改动和分支更新使用同一份工作区。已有代码托管任务收到新反馈时，继续沿用原 Task 和模型快照，从新 Run 为原分支重新申请审批并继续交付。历史 Run 保留其已执行的配置。

固定提交归档复用文件级敏感路径规则。若归档移除了受限路径，原生运行使用该 Task 的独立工作卷和原生日志，避免旧卷或历史内容把已排除的文件重新交给模型。未受影响的 Task 沿用原卷。

基于已获准的项目沙箱基础镜像构建 `runtimes/sandbox/coding-tools`，固定 `SANDBOX_IMAGE` 与 `NODE_IMAGE`，将镜像 ID 或不可变引用设为 API、工程 Worker、协调 Main 和 effects 进程的 `WEORA_NATIVE_RPC_IMAGE`。同时启用 `WEORA_RUN_RUNTIME=pi` 并配置 `WEORA_REPOSITORY_CACHE_PATH`。这里 `pi` 是 Weora 运行族开关，具体任务引擎仍由 Harness 选择；不是强制全部使用 Pi。

全部相关进程必须使用同一候选源码版本和配置，避免 API 已改而协调进程仍加载旧代码。Worker 访问管理员配置的 Docker 守护进程；测试机也支持通过 `WEORA_SANDBOX_CLI_EXECUTABLE` 使用现有 Podman 包装器。现有任务创建和继续接口保持兼容，旧 SDK 会话使用对应历史 Runtime，不将旧消息强制写成另一引擎的原生日志。

有飞书入站的部署为 `weora.coordination.control` 保留独立消费者。该队列从持久 Inbox 读取消息并投递 Main 和效果。工程运行使用 `weora.runs` 消费者，Main 和 Outbox 各用自己的队列。长运行占满两个工程执行槽时仍须处理插话和停止。测试机用 `weora-coordination-control.service` 保留这条执行容量。

会话卷需要稳定路由、配额、备份及访问回收。模型超时、运行超时和容器退出上限分别管理。部署记录应包含源码候选 SHA、镜像 ID、进程版本核对、重启顺序与回滚路径；真实入口验收使用工作空间已配置的模型连接。
